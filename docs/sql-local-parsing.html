根因是建表体捕获被截断：原实现用 \(([\s\S]*?)\) 非贪婪匹配， 而尾部又全是可选子句，于是第一个带括号的列类型就成了结束点。 

输入：CREATE TABLE users (
  user_id INT PRIMARY KEY,
  username VARCHAR(50) NOT NULL,
  dept_id INT,
  FOREIGN KEY (dept_id) REFERENCES dept(id)
) COMMENT='用户表';

旧正则捕获到的 body："\n  user_id INT PRIMARY KEY,\n  username VARCHAR(50"
                                        ↑ 到此为止 → 列、外键、表级主键全部丢失

由于真实 schema 几乎必有 VARCHAR(n)，这条路径实际上从未产出过关系—— 这也解释了为什么之前只有配了 API Key 的 AI 分支"能用"。 现在改为引号与注释感知的括号配对扫描，并按 ); 边界逐条推进。

命名与联系动词的推断规则

目标优先级
实体名COMMENT '...' / COMMENT ON TABLE → 内置业务词表 → 建表语句上方 -- 注释 → 原表名
联系名外键列名动词表（manager_id→管理、from_user→发送）→ 列 COMMENT → 关联
多重性外键列被主键或 UNIQUE 覆盖 → 1:1；否则 1:N

两处刻意的取舍：
· 联系名用动词表而不是列注释——读法是「父实体 ——动词—— 子实体」，而列注释多为名词短语（如「所属部门」），直接套进这个方向读不通；列注释只作兜底。
· 词表排在"上方 -- 注释"之前——分节注释（-- 多对多连接表）很常见，让它盖掉 user_role → 用户角色 这种确定的翻译并不划算； 同时过滤掉了 mysqldump 的 -- Table structure for xxx 这类工具噪声。

端到端渲染（本地解析 + 本地布局，未调用任何 AI）

默认折叠纯连接表后为 11 个实体、11 个联系（含 1 条 M:N、2 条 1:1、1 条自反）。实体位置由 utils/erLayout.ts 按外键结构排布（核居中起始 + 交叉最小化 + 真实寻线精修），几何校验：实体/菱形/标注零重叠、连线零穿越。详见 er-local-layout.html。

仍然需要 AI 的部分

本地解析覆盖的是结构化信息（表、列、约束、注释）。以下仍然更适合 AI，建议保留为可选增强而非默认路径：
· 自然语言需求（"帮我做一个图书借阅系统的 ER 图"）——没有 DDL 就没有可解析的结构；
· 词表未命中的业务词汇翻译（如 t_pms_apply 这类无注释的缩写）；
· 不规范 schema 的语义补全（没有外键、只靠 xxx_id 命名约定，且不在动词表内）。

另外两处已知限制：多对多连接表目前按物理模型展开为两条 1:N（保留连接表实体），没有合成概念层的 N:M 联系； 实体位置仍是顺序网格，没有基于外键方向的本地自动布局。
