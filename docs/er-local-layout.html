本地 ER 布局：不依赖 AI

核居中 → 代理粗排 → 真实寻线精修 → 连续坐标微调；寻线器会避让已画好的线；基数标注 1/N/M 也改成沿线全局放置。 输出绝对坐标 x/y，可微调、刷新不丢。

本轮①：基数标注（1 / N / M）的布局重做

旧做法是"每条联系各自在端点附近找个位置，撞到别人就往一个方向推 15px"。 主表度数一大（十几个联系），这些标注会被依次推成一列 —— 既远离自己的线，也看不出属于哪条联系， 就是你截图里那种混乱。

做法说明
候选点只沿自己的折线从所属实体出发，按 14 → 200px 由近及远采样，再沿线法向小幅偏移（±13 / ±24 / 压线）
硬约束候选点压到实体框直接淘汰（借障碍索引查询，自带 10px 净空）
梯度罚分离已放标注越近罚得越多；离菱形越近同理；压在其它线上再扣一点（文字有白色描边，压线仍可读）
受限者优先先放"可用候选最少"的标注，避免最后无处可放

实测（13 表 schema，22 个标注）：

标注质量指标重构前重构后
标注离自己那条线的平均距离最大 180 px（被推成一列）16.5 px
标注离自己那条线的最大距离180 px24 px
标注之间的最小间距15 px24 px

本轮②：矩形改直角 + 实体字号放大一号

  • 实体矩形去掉圆角（rx="4" → 无），全图 0 个圆角矩形；
  • 实体标签字号 12 → 14；
  • 顺手把框宽估算统一成布局与渲染共用一套（estimateEntityWidth + ER_ENTITY_FONT）—— 以前渲染和布局各写一份宽度公式，改字号很容易只改一边，导致"算出来的宽度"和"画出来的宽度"不一致。

本轮③：耗时预算放到 5s 级，并加"多起点"

既然 5s 可以接受，就把它花在搜索上：

  • 多起点：网格"形状"（列数）对版式影响很大，而 sqrt(n) 只是经验值 —— 现在对 3 种候选列数各跑一遍"初始分配 + 代理粗排"，用代理代价选最好的那个，再让它独享后面昂贵的精修与连续微调；
  • 精修（真实寻线代价）与连续坐标微调的评估次数预算整体放大 2~3 倍；
  • 关键提速：布局评估时跳过"基数标注放置"（routeRelations(..., { skipCards: true })）—— 布局代价只需要路径与菱形落点，标注留到最终渲染再放。这一项让单次评估便宜了近 4 倍。

本轮④：顺手修掉一个真 bug（菱形重叠）

用"12 个超长实体名 + 11 条联系"的极端用例压力测试时暴露：两个菱形中心只差 13 px（菱形宽 56）→ 直接叠在一起。

菱形兜底三层：
① 末段/各段采样 t      —— 有冲突检查 ✓
② 全段扩大到 9 个 t    —— 有冲突检查 ✓
③ 沿法线递增探测       —— 探测半径只到 6 步（±396px），且**最后一层没有冲突检查**：
                          if (!diamond) diamond = { x: mx, y: my }   ← 硬放回中点
长标签让列变宽、主表周围十几个菱形互相竞争时，6 步探不到空位 → 直接重叠。

修法：探测半径 6 → 24 步（±1584px）；最后一层兜底改成"取离所有已有菱形最远的候选"，而不是硬放回中点。修后该用例的菱形净空从重叠变为 43.9 px。

双核与"指定中心"

仍然存在的不足

  • 寻线避让是顺序贪心：先画的线占优，没有 rip-up 重路由（先画的不会为后画的让路）；
  • 避让换来更长的线与更大的画布，"少交叉优先"的取舍已固定；
  • 标注放置也是贪心（受限者优先），理论上可以用二分图匹配做得更均匀；
  • 菱形离线仍有约 5~6 px/个的残留（寻线器自己的落点在拥挤时无可避免）；
  • 连续微调只在 ≤80 实体运行；超长标签会让列很宽（列宽由最宽标签决定）；
  • 核评分仍以结构指标为主，业务语义靠用户在下拉里覆盖。
